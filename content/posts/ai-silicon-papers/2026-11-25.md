**核心问题：一条失败经验即使值得保存，为什么也未必应该在新任务开始时交给 Agent？**

## 论文卡片

*Self-Evolving Beyond Human-Crafted Experience for EDA Scripting*，arXiv **2026-11-19 v1**。预印本，页面注明已投稿 DATE 2027，不代表已录用。

作者：Yang Liu、Shengbo Tong、Xiyuan Chen、Shiwei Hou、Sen Yuan、Hao Wang、Yanfeng Li、Hongwen Li、Yiming Zhu、Zhuolun He、Wenjian Yu。机构：CXMT、清华大学、中国科学技术大学。

定位：冻结底层模型，从 PyAether 脚本任务的执行轨迹中积累外部知识的 Agent 系统；研究如何约束经验的写入、检索与整轮更新。

## 简短导读：知道“曾经错过”，不等于知道“这次会错”

ZhuLong-SE 把历史保存为原始轨迹、聚合模式和版本化技能。写入前，外部隐藏测试的通过／失败结论覆盖代理的自报成功。若最终尝试仍报错，就反思错误；若自测通过却没通过隐藏测试，则走另一条反思路径，避免把日志里已经修好的旧错误当作尚未解决的问题。

读取时，系统也不把所有经验一视同仁。任务开始前，成功方案只提供 API 名称，去掉调用顺序与参数；任务描述还会移除识别具体实例的细节。**避坑经验不提前注入，而是在实际发生错误后按需查询。** 作者的解释是：任务描述能提示“要做什么”，却未必能预测代理将误用哪个 API。

这让记忆的作用从“多给一些背景”变成“在适当条件下给出有限提示”。保存资格与调用时机，是两个独立判断。

## 证据与限制

首先要分开两组实验。158 个任务上 **92.4% Pass@1** 的结果来自增强后的任务流程，包含检索、静态检查、隔离沙箱与人工经验，**关闭了自演化**。每个配置只跑一次，逐步加入组件的消融也不能完整分离组件间的交互，不能把这个数字归因于自动积累经验。

自演化另用实例互不重叠的 **98／20／40** 训练、验证、测试划分，测试集按测试代码长度和 API 数量集中较难任务。底层模型固定为 DeepSeek-V4-Pro-Preview；下表是 40 个测试任务上五次独立运行的均值及标准差（§V-B，表 III）。Pass@1 指一次提交通过真实执行中的隐藏测试，不是普遍正确性的证明。

| 知识状态 | 测试 Pass@1 |
| --- | --- |
| Bare：无演化知识 | 66.0% ± 7.2 |
| 人工经验基线 | 77.5% ± 5.3 |
| 第二轮演化 | 80.0% ± 3.1 |
| 第三轮演化 | 75.5% ± 6.7 |

第二轮均值比人工基线高 **2.5 个百分点**，但样本小、仅五次运行，论文未给出足以支持显著优势的统计检验。第三轮知识更多却表现下降；其验证分数也从 88.0% 降到 80.0%，越过“相对上一轮最多下降五个百分点”的门槛，因此整轮回滚。作者将其解释为过拟合；更保守的读法是，两套留出数据都观察到退化，单凭这些汇总数还不能唯一识别退化原因。

与核心问题最直接相关的是**冻结第二轮知识后的读取消融**（表 V）：在 20 个验证任务、五次运行中，完整配置为 88.0% ± 2.7；提前注入避坑经验变为 **80.0% ± 5.0**，提供完整调用序列而非仅名称则为 **83.3% ± 5.8**。这支持该配置下“注入更多细节未必更好”，但不证明所有负面知识都应延迟调用，也不直接量出跨任务答案抄用减少了多少。问题侧与答案侧 embedding 在这里同为 88.0%，没有测出性能差异。

写入侧也有边界。固定 24 个失败任务轨迹的离线消融中，不使用外部判定覆盖自报成功，会让其中 12 个任务产生至少一条被错误标为已验证的经验。但这组实验主要数知识条目，**不是完整的后续任务质量比较**。记录适用边界的作用不能由条目数判定；需要跨两个批次反证才触发的过滤器，在单轮回放中根本未被触发。论文明确承认这两项机制在该实验中尚未验证有效。

## 重点阅读

- **§IV-A–B**：外部结果如何改变反思路径，以及“已验证”标签究竟依据什么。
- **§IV-C**：成功方案与避坑经验为什么采用不同的读取方式。
- **§IV-D、§V-B 表 III**：验证集决定回滚，测试集用于报告；留意小样本与反复使用验证集的边界。
- **§V-B 表 IV–V**：分别区分“知识条目发生变化”与“任务表现发生变化”。

## 思想启发

以下是导读者的延伸：经验的可信度不是一个脱离情境的总分。过去确实发生过某种错误，只能支持“这个风险存在”；要让提醒帮助当前决策，还需要当前情境与风险之间的联系。

因此，不提前提供完整答案，并不只是信息损失。它可能留下必要的重新推理空间，避免旧轨迹替新任务做决定。不过，本文只在一个工具生态与有限划分上展示了这种收益，尚不能把“信息更少”提升为普遍原则。

## 三个开放问题

### 1. 避坑知识提前注入后的下降，说明知识不相关，还是说明提醒改变了代理的注意力？

<details>
<summary>参考思路（展开）</summary>

作者强调任务描述无法预测具体 API 误用，但结果也与注意力分散、过度防御或错误类比相容。消融改变了注入方式，支持这套方式在该验证集上有害，却没有把各种心理式解释分别验证。负面经验为真，与提醒产生净收益，可以同时不成立。

</details>

### 2. 只保留 API 名称，究竟在转移方法，还是仍在提供部分答案？

<details>
<summary>参考思路（展开）</summary>

删除顺序与参数降低了照搬完整解法的机会，但选对 API 本身也可能是任务的关键难点。实例不重叠不等于概念或解法不重叠。名称提示可以是合理的领域知识，也可以在高度相似任务间接近答案线索；两者的边界取决于希望评测的能力。

</details>

### 3. 验证门成功拒绝第三轮，是否足以说明系统能够长期自我纠错？

<details>
<summary>参考思路（展开）</summary>

这次回滚阻止了一个观察到的退化状态被采用。但不断用同一小验证集选择更新，可能逐步适应这组数据；五个百分点阈值也容许较小退化。一次正确拒绝证明了机制实际起作用，不等于证明它在长期更新、工具变化或分布改变后仍可靠。

</details>
