今天选择两篇**过去七天内发表的原创工程实践文章**：Hugging Face 将模型训练直接放进部署时使用的 Agent Harness；Airbnb 则把编码代理的离线任务评测与部署后的费用、请求分布、限流数据闭环。两者讨论的不是单独模型的 Benchmark 排名，而是**特定 Harness 与真实工作负载下，完成任务的质量、工具行为、成本如何共同优化**。

两篇原文分别发表于 2026-11-20、2026-11-18，均为作者/工程团队报告；实验成绩及企业成本案例未经独立复现。本文不将不同 Harness 的绝对分数或离线成本直接当作跨产品、跨组织可比指标。

## 1. Introducing harness adapters: adapt your favorite model to your harness to improve performance and cost

- **作者/来源：** Younes Belkada、Ben Burtenshaw、Nathan Habib 等 / Hugging Face 工程博客
- **发布日期：** 2026-11-20
- **原文：** https://huggingface.co/blog/harness-adapters-at-scale
- **公开模型、数据与工具集合：** https://huggingface.co/collections/harness-hub
- **相关技术：** Agent Harness、Qwen3.8-27B、LoRA、GRPO、TRL AsyncGRPOTrainer、OpenEnv、Harbor、vLLM、Tool Efficiency

**推荐理由：** 大模型在通用训练中未必学会某个 Harness 的工具格式、上下文机制与动作节奏。文章给出可复现的**在原生 Agent 循环中训练 LoRA**的方法：冻结 Qwen3.8-27B，分别在 Pi、OpenCode、Hermes Agent 中收集真实轨迹、利用可执行验证器打分，并尝试把专用适配器合并。它让「Harness 与模型的联合优化」从修改 Prompt 或框架代码，扩展为具有可测量行为变化的模型适配。

**3 条核心要点：**

1. **保留真实 Harness 的强化学习闭环。** 分别固定 Pi 1.5.2、OpenCode 2.2.7、Hermes Agent v0.22.6，使用 TRL `AsyncGRPOTrainer`、OpenEnv/Harbor，在未重写的 Agent 循环中采样；代理捕获模型交互，奖励由任务验证正确性与小幅工具效率加分（0.1）组成。训练数据混合 750 个编码任务与 300 个 Termgrade 任务，并用规则型 safeagents 插件拦截危险工具调用；这不能替代真正的生产隔离。
2. **专用 LoRA 同时改善成功率与工具效率。** 作者报告 Pi 在 SWE-bench Pro 最难的 51 题中，从 **39.2% 提升至 64.7% pass@1**；在 Terminal-Bench 2.1 上提升 **16.3 个百分点**。三个专用适配器在各自 Harness 的两个基准中都优于同配置基线；仅统计**双方都解决的任务**，SWE-bench Pro 的工具调用减少 **56%–72%**。不能把它解释为所有任务的 Token、成本或时延都同比例下降。
3. **跨 Harness 合并带来权衡，且评测边界重要。** 将三个 rank-32 LoRA 拼成 rank-96，并各以 0.5 权重合并的 super-adapter，在开启 thinking 的六组 Harness×基准对照上，平均 pass@1 **55.5%→63.5%**，但 Pi/SWE-bench Pro 为 **74%→74%**，并非普遍提升。合并权重在 Terminal-Bench 上选择，相关得分可能略乐观；不同 Harness 的自动上下文压缩行为不同，不能直接横向比较；300 道分布外 AutomationBench 任务也未见明确可迁移收益。论文式数值均为团队自行评测，仍需复现。

> **核心启示：** 当某个 Coding Agent 的工具调用过多、计划反复失败时，不只尝试改 Prompt 或换大模型，也可用固定版本 Harness + 验收器训练小型适配器，分别检查成功率、调用量、Token 与跨任务退化。

## 2. How Airbnb uses cost per task to operate coding agents on Amazon Bedrock

- **作者/来源：** Alan Yao、Rashim Gupta、Sang Kong、Jayadev Vadakkanmarveettil / Airbnb × AWS Machine Learning Blog
- **发布日期：** 2026-11-18
- **原文：** https://aws.amazon.com/blogs/machine-learning/how-airbnb-uses-cost-per-task-to-operate-coding-agents-on-amazon-bedrock/
- **相关技术：** AirChat、AirChat Remote、LLM Gateway、Amazon Bedrock、Harbor、Agent Eval、Prompt Caching、CloudWatch、Cost/Task、Effort Ceiling、Quota

**推荐理由：** Airbnb 已有数千名每周使用 AirChat 的工程与相邻职能用户。文章展示从真实代码变更和 Review 构造隔离 Eval、根据任务得分与总成本选模型，到生产环境按缓存、请求频率、延迟与限流重新审视选择的完整做法。它指出一个容易忽略的陷阱：**离线每任务成本相近的模型，上线后可能因用户行为变化而让每用户周成本大幅上升**。

**3 条核心要点：**

1. **模型选型看完整任务，不看单次请求。** Airbnb 将真实代码变更、审查意见和隐性决策做成七套任务集；每题有冻结环境、指令、验收器和参考解。按**非缓存输入、缓存读取、缓存写入、输出**四种 Token 分别计价并累计整个任务，还把推理力度作为独立配置；一个模型的 low→high 只使评分提高 **0.8 分**，但每任务成本增至 **2.5 倍**，因此在网关设置默认模型和 effort ceiling。
2. **线上成本与离线 Eval 发生偏离。** Airbnb 的匿名 **Model A** 离线评分比旧模型高逾 3 分、任务成本相近，上线后平均每用户每周花费却高出数倍：单请求约 **3 倍**费用，用户平均请求量也约 **3 倍**；输出 Token 只占请求费用约十分之一，大部分费用来自反复读取缓存上下文。后来同组重度用户切换到更高分、任务成本约为 Model A 六分之一的新模型，第一整周主要模型的支出约降至**原来的七分之一**。这是单组织的匿名案例，不应据此推算任何模型的通用倍数。
3. **建立发布后测量和容量治理。** 网关关联 model/client/team/user 的聚合记录，CloudWatch 分离 TTFT、输出 Token、OTPS、请求限流与配额预留；示例中延迟上升 40% 的根因是提示修改使输出长度增加 50%，而非模型变慢。入站配额与最终 Token 账单不同，适度调低 `max_tokens` 可减少预留，但要监控截断；对主要模型事先测好同等质量的备用路由，且对调用日志严格限制访问与保留时间。

> **核心启示：** 选型指标至少应同时涵盖任务通过质量、每任务费用、每用户每周成本、请求频率、缓存命中/读写比例、延迟及配额。离线评测选择默认值，生产观测检验默认值是否仍合理。

## 今日思考

两篇文章分别回答 Agent Software Factory 的不同问题：**如何使模型更适应固定 Harness 与任务分布？如何确认这种离线改进在真实团队中仍然划算？**

**固定 Harness/版本与任务集 → 原生轨迹/验证器 → 专用 LoRA 或模型参数选择 → 任务质量与成本 Eval → 生产用户行为/缓存/时延观测 → 回归验收和调整。**

值得独立验证：同一组真实仓库任务分别运行通用模型、Harness 专用 LoRA 和合并 LoRA，在相同预算/推理设置下记录完整任务成功率、工具调用、缓存成本、墙钟时延与长轨迹回归；再按真实任务/用户频率模拟一周成本。**训练评测、生产成本和安全边界要分别验收**，不能仅凭 Benchmark 提升就宣布 Software Factory 更高效。

**证据边界：** Hugging Face 的评测存在固定 Harness 版本、训练时关闭 thinking、选择合并权重使用部分基准等条件，跨 Harness 绝对分数不可直接比较；Airbnb 只披露匿名模型和聚合统计，不能独立审计真实内部账单。两篇均为工程团队的一手文章，但没有跨组织可重复的效果保证。
