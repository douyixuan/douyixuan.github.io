今天选取两项**最近七天的新成果**：一篇 11 月 16 日首次提交的 Agent 编程语言论文，以及一篇 11 月 16 日发布的微软研究团队原创工程解读（其配套论文早在 10 月 15 日首次公开，故本文以**本周新发表的工程解读**入选，不将旧论文误写成新论文）。二者都在思考怎样让 Agent 工具链更高效，但优化边界不同：前者通过**更明确的程序语义**帮助编译器和运行时优化，后者通过**多次任务积累的经验**降低已有 Coding Agent 的执行开销。

共同问题：**哪些 Agent 控制逻辑应该成为编译器能够理解的程序结构，哪些优化可以由不侵入模型和 Harness 的外部控制器完成？** 下面的效果数字来自论文作者及微软研究博客，尚未经独立复现。

## 1. Agent-Native by Design: A Programming Language for Agentic Applications

- **作者/来源：** Jayanaka L. Dantanarayana、Savini Kashmira、Xiaoyu Ma、Malitha Prabhashana、Lingjia Tang、Jason Mars / University of Michigan、Shanghai Jiao Tong University、Jaseci Labs；arXiv 研究预印本
- **首次提交：** 2026-11-16 16:01:06 UTC（北京时间 2026-11-17 00:01）
- **arXiv 原文：** https://arxiv.org/abs/2611.21298
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.21298
- **相关技术：** Jac、Agent-Native Programming、Programming Languages、Object-Spatial Programming、by llm()、Model-Guided Routing、Compiler/Runtime Optimization

**推荐理由：** 许多 Agent SDK/Framework 把模型调用、工作流状态和模型决定的分支执行分散在应用与框架代码之间，导致开发者需要重复维护状态同步和路由映射，编译器也缺乏完整依赖视图。论文探索用 **Jac（Python 超集）**把三者纳入同一执行语义：用语言级结构表达 Agent，而不是在宿主语言上拼接模型调用与控制流。值得重点阅读它如何为编译分析、推测执行和服务分区提供可检查的前提。

**3 条核心要点：**

1. **统一模型、工作流和路由的语言语义。** `by llm()` 表达带类型的模型操作与工具调用，Object-Spatial Programming 用节点、边与 walker 承载执行图和状态，`visit ... by llm()` 从当前可执行的工作流步骤推导模型路由候选，并调度所选步骤。它避免另外维护一份“模型可能选择什么”和“程序真的能跳到哪里”的映射，也让编译器看见状态依赖。
2. **减少的是 AI 集成样板，而非保证总代码或任务质量成倍改善。** 在五个应用基准与五类对照中，专家编写的 Jac 版本相对原生 OpenAI SDK 减少了 **1.8–8.7 倍 AI-integration code**，观察到的任务质量相近；让 Claude Code 和 Codex 自行构建应用时，相对 SDK 构建过程聚合的 Token 用量分别减少 **48% 和 51%**。这些结果取决于测试应用、实现方式与任务设计，不是所有 Agent 的通用节省率。
3. **编译器可以优化，但必须证明适用条件。** 论文展示由程序分析与运行时检查支撑的**推测模型请求**和**服务分区**；三项适用的五个基准中，推测执行对路由决策的中位时延改善为 **29%–39%**。优化依赖候选路径、状态读写与绑定可以安全分析等条件，不能无约束地提前执行具有副作用的工具调用，更不能把通过研究测试等同于形式化证明完整系统正确。

> **核心启示：** 当 Agent Workflow 成为编译器可见的程序，优化对象便从“改善 Prompt”扩展到“分析程序依赖、执行语义和安全的运行时变换”。这与 LLVM/MLIR 等编译器对显式 IR 和可证明转换条件的要求高度相通。

## 2. TokenEconomizer: Learning from Experience to Make AI Coding Agents More Efficient

- **作者/来源：** Aaron J. Li、Weijia Xu、Chandan Singh、Zixiao Chen、Jeevana Priya Inala 等 / Microsoft Research、UC Berkeley、Microsoft Security
- **工程文章发布日期：** 2026-11-16（**本周新文章**）；配套论文首次提交 **2026-10-15 23:06 UTC**（早于本周）
- **工程原文：** https://www.microsoft.com/en-us/research/blog/tokeneconomizer-learning-from-experience-to-make-ai-coding-agents-more-efficient/
- **配套论文 arXiv：** https://arxiv.org/abs/2610.22732
- **配套论文 AlphaXiv：** https://www.alphaxiv.org/abs/2610.22732
- **开源实现：** https://github.com/microsoft/TokenEconomizer
- **相关技术：** Coding Agents、Repository Experience、Micro-Skills、Tool Pruning、Failure-Loop Intervention、Black-Box Optimization、Token Cost

**推荐理由：** Coding Agent 在同一个仓库连续处理 Issue 时，往往不断重新发现相同测试命令、重复加载不用的工具 Schema、或者陷入相同错误循环。微软研究团队将“一个仓库的连续任务流”而不是“单个任务”作为优化单位，提供可运行的外挂式控制器；不用修改 Claude Code、Codex 等 Agent 的模型和核心循环，也能利用历史轨迹控制上下文、工具集和纠错时机。

**3 条核心要点：**

1. **通过真实轨迹识别三类重复开销。** 作者先在六个仓库的 60 个 SWE-Bench 任务中观察：至少完成五项任务之后，**30%** 的工具调用重复了本仓库之前的操作，而跨仓库匹配仅 **7%**；加载的 **23** 个工具描述中有 **16** 个从未使用；失败任务占 **17%**，却消耗 **32%** 成本。它们是可以改善的开销信号，并不意味着所有重复调用都应该删除。
2. **外挂控制器实行动态、可撤销的三类干预。** 从已完成会话中学习仓库特定的短小 **micro-skills**，在多次证据支持后注入，遇到矛盾可撤销；按历史使用与相关性裁剪工具，但保留关键文件/命令操作并允许恢复；遇到疑似失败循环时借助判断模型提醒转向，开源插件在持续卡住时通知开发者。控制器的额外模型调用成本也纳入评测。
3. **连续任务上节省费用，成功率总体保持接近。** 在六仓库、**277** 个 SWE-Bench 任务、**五种 Agent–模型组合**上，平均缓存计价成本降低 **18.4%–30.9%**，全部 30 组仓库×组合单元均降低成本，五种组合中四种 Pass@1 有改善；到第六项任务各仓库的累计成本才均低于基线。Web-Bench 节省 **16.0%–21.2%**，安全审计任务 **6.4%–19.6%**。这是作者受控评测中的**计价成本**变化，不等于响应时延、原始 Token 数或生产可靠性同比例改善。

> **核心启示：** Agent Harness 可以在不修改模型的情况下学习具体仓库的操作习惯；“跨任务经验”应作为有版本和证据、可淘汰的运行时策略，而不是把所有旧会话完整塞进 Prompt。

## 今日思考

两篇研究提供了互补的优化层次：

**Agent-Native Language → 显式控制流/状态/模型调用 → 编译器分析 → 有条件的安全运行时优化。**

**Black-Box Controller → 历史轨迹 → Micro-Skill/Tool Policy/Loop Detection → 更低的重复执行成本。**

组合时应避免把“编译器能分析的结构”与“控制器从历史推断的经验”混为一谈。**程序语义**决定何种转换合法，**经验策略**决定在哪个仓库、哪次任务值得尝试。值得验证的是：将 Mic​​ro-Skill、工具可用性与失败循环检测分别加入同一仓库多任务基线时，对 Pass@1、缓存计价成本、wall-clock 时延和回归稳定性的边际影响。

**证据边界：** Jac 论文在五个研究应用上比较代码量、构建 Token 和特定优化的延迟，不能直接推导真实大型仓库的总体收益；TokenEconomizer 的节省需要多任务历史，首次执行可能更贵。Jac 的 arXiv 与 alphaXiv 对应正文已由文献接口核对（AlphaXiv 标准网页独立 HTTP 抓取失败）；TokenEconomizer 的 arXiv 与 AlphaXiv 标准网页均已读取并核对论文标题、作者和编号。两者成果尚未独立复现。
