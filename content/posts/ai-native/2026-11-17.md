今天选择两篇**过去七天的原创多代理研究**（分别于 2026 年 11 月 12 日与 13 日首次公开）。它们研究的不是单个模型的能力上限，而是多个模型经过**任务委派、证据转述与回答聚合**后，系统为何会得到错误结果，以及可以在何种假设下改善聚合安全性。

共同问题：**主 Agent 自己能够识别的伪造证据，为什么经子 Agent 转述就会被采信？当多个 Agent 贡献互相冲突的答案时，谁有权决定最终结论？** 两篇为研究论文，以下数值来自作者给定实验，不应直接外推为真实代码仓库中所有任务的失败率或安全保证。

## 1. Only as Safe as the Weakest Agent: A Break That Appears Only When the System Is Multi-Agent

- **作者/来源：** Keegan Wang（Carnegie Mellon University / Prosaic Intelligence）、Anantika Mannby（University of Southern California / Prosaic Intelligence）；NeurIPS 2026 Meta-Agents Workshop 接收论文 / arXiv
- **首次提交：** 2026-11-12 21:14:49 UTC（北京时间 2026-11-13 05:14）
- **arXiv 原文：** https://arxiv.org/abs/2611.17520
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.17520
- **相关技术：** Coding Agent、Native Subagent、Harness、Delegation、Evidence Laundering、Prompt Injection、Trust Boundary

**推荐理由：** 很多 Coding Agent 把检索、文件阅读等工作交给更便宜的子模型，再由高能力主模型作决定。本文没有只在自造提示中模拟协作，而是使用未修改的 Claude Code、Codex CLI 及参考 Harness，对比**同一份文档由主模型亲自读**和**经弱子代理转述**的结果。它为“分工节省模型成本，却可能改变证据可信度”提供了可量化的系统层实验。

**3 条核心要点：**

1. **在文件存储中投放伪造记录，观察主代理是否改变原本正确的答案。** 研究使用 180 个虚构事实的二选一问题，伪造档案携带可检查的矛盾（例如所谓更正的日期早于原始记录、缺少正式档案行）。强主代理直接阅读时，特定攻击条件下通常能发现伪造；由弱子代理检索并汇报时，主代理无法直接接触原始证据，容易把子代理解释当作事实。研究把原先答对、收到伪造记录后改错称为 harmful revision。
2. **风险来自弱读者与交付链路，不能用主模型的安全性替代系统评估。** Claude Code 的 Opus 5 → Haiku 4.5，在 stacked 伪造条件下由主代理直接阅读为 **1/180** 次有害修正，委派后升至 **75/180**；Codex 的 GPT-5.6 Sol → Terra，在 gloss 条件下从 **0/180** 升至 **44/180**。换成同等级子代理，所测对应情形下降到 0/180 或 1/180。不同伪造类型、不同 Harness 的敏感性并不一致，不应将上述比率理解成产品通用漏洞率。
3. **证据转述会放大错误，模型的强弱与信息通道必须分别测量。** 作者另在模拟的多模型传递实验中发现，五个本来单独判断基本可靠的聚合者，在收到被污染的子代理结论后，**751/757** 次转述了错误。该数据来自模拟传递环节，不能混同前述原生 Coding Agent 实验。文章说明：只记录“主代理使用哪个大模型”不足以证明系统安全，还需检查谁读取了原始证据、谁传递了结论以及委派的工具边界。

> **核心启示：** 子代理输出应被视为带来源的待核查证据，而不是与第一手工具输出同等可信的结论。尤其在委派给更弱模型进行搜索、总结和审查时，主代理失去对原始材料的直接可见性可能成为关键风险。

## 2. Securing Multi-Agent Systems by Design

- **作者/来源：** Xilong Wang、Xiaoxing Chen、Neil Gong / Duke University；arXiv 研究预印本
- **首次提交：** 2026-11-13 08:22:06 UTC（北京时间 2026-11-13 16:22）
- **arXiv 原文：** https://arxiv.org/abs/2611.17883
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.17883
- **相关技术：** Multi-Agent Systems、ReMA、SecMAS、Secure Aggregation、Embedding、Robust Consensus、Agent Security

**推荐理由：** 第一篇揭示了子代理报告被过度信任的问题，本篇则研究主 Agent 在汇总多份子代理回答时，如何抵御**少数恶意代理精心设计的结果操纵**。作者提出 ReMA（Response Manipulation Attacks）来专门攻击聚合规则，再提出 SecMAS，用回答之间的语义一致性选择结果，并讨论理论保证所依赖的假设。它提供了一个可讨论、可复现实验的聚合层防线，而不是简单要求模型“不要受骗”。

**3 条核心要点：**

1. **把恶意响应建模成针对聚合器的优化问题。** ReMA 区分使最终答案偏离事实的非定向攻击，和把结果导向攻击者指定内容的定向攻击；通过替身多代理系统反复评估、调整恶意响应。它还评估攻击者不了解管理模型、聚合规则或其他代理回答的情形，说明仅靠隐藏聚合实现不能构成充分防御。
2. **SecMAS 采用语义多数聚合，而非直接汇总全部回答。** 对同一子任务设置多个独立响应，嵌入为向量、计算两两余弦相似度，选择与足够大一组其他回答最一致的响应。其思路依赖**良性代理占多数、良性回答在语义空间中聚集且恶意回答不形成更强一致团体**等条件；论文给出的理论界限是语义相似度性质，不是对任意问题事实正确性的无条件证明。
3. **在作者测试场景下优于现有聚合规则，但有威胁模型与评估器边界。** 对摘要、置信度投票、基于评估模型的选优和注入过滤等基线，ReMA 某些条件下的攻击成功率达到 **1.00**；即便攻击者不知道三类关键内部信息，新闻场景针对普通 Summarization 的非定向和定向成功率仍为 **0.61 / 0.49**。SecMAS 在作者评测的教育、金融、医疗、法律、新闻任务中，把所测试攻击的成功率压到接近未受攻击基线，并保持近似正常任务效用。这些数字基于作者选取的场景、固定恶意比例以及 LLM/向量相似度评估，并不意味着能抵御多数代理合谋或一致地给出错误答案。

> **核心启示：** 多 Agent 汇总不能默认“答案多就是可靠”，更不能把某个代理的自信分数当成事实证据；聚合规则需要显式定义威胁模型、可接受的恶意比例与失败条件。

## 今日思考

**委派改变了证据被谁读取，聚合改变了谁的判断成为最终答案。** 第一篇说明强主 Agent 并不会自动修复弱子 Agent 带回的错误；第二篇说明即使有多个回答，聚合器也可能成为攻击目标。

两篇可以合起来理解为一个待验证的设计问题：

**Original Evidence → Provenance / Trust Boundary → Independent Readers → Robust Aggregation → Source Recheck → Action Authorization。**

这不是两篇论文已经共同验证过的生产方案。尤其对会修改仓库、合并 PR、发布网站的软件工厂，还必须区分事实检索错误、代码测试失败与授权操作风险：多数意见不能代替原始测试、Commit 证据或独立的权限控制。值得追问：如果多数子 Agent 共享相同污染源，语义一致性是否只是放大了共同错误？怎样让主代理在高影响操作前重新读取原始材料？

**证据边界：** 第一篇在原生 Claude Code/Codex 的任务是虚构档案检索与事实问答，而不是实际代码漏洞修复；其 751/757 为模拟传递环节。第二篇的防御依赖良性多数与语义相似性假设，攻击成功与正常效用指标由论文定义的评估器测量。两篇 arXiv 论文元数据与 AlphaXiv 对应论文正文均已核对，AlphaXiv 网页独立 HTTP 访问未确认。
