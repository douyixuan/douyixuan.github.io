今天选择两篇**过去七天首次公开的原创研究**：一篇把 Coding Agent 放进具有项目看板、同事、历史记录与 CI 的模拟软件组织，检验它是否真正查清需求并完成工作；另一篇把自然语言 Skill 当作部分可编译、可定点修改的程序，用分析和回归测试维护 Agent 的执行知识。

共同问题：**即使 Agent 会写代码，它能否持续追踪真实需求；即使 Skill 能改进一次任务，它能否避免破坏原本正确的行为？** 两篇均为未经独立复现的研究预印本。前者使用受控的模拟组织与真实开源仓库，后者使用单轮问答基准，不能直接把实验结果当成企业生产环境的交付率。

## 1. SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations

- **作者/来源：** Xinping Lei、Minghao Liu、Ruijie Zhu、Xiaohui Hu 等（共 26 位作者）/ arXiv，软件工程与 AI 研究预印本
- **首次提交：** 2026-11-15 19:39:01 UTC（北京时间 2026-11-16 03:39）
- **arXiv 原文：** https://arxiv.org/abs/2611.20218
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.20218
- **相关技术：** Coding Agent、Requirements Engineering、Organizational Context、Multi-Agent Interaction、F2P/P2P Testing、Software Factory

**推荐理由：** 传统 SWE-bench 式评测经常直接给 Agent 一份相对明确的 Issue；真实团队里，需求则散落在同事的口头解释、版本化文档、看板和旧讨论中，而且可能互相矛盾。SWE-CoWork 在真实开源代码仓库周围构建受控的工程组织，要求 Agent **主动向正确的人求证、追踪延期答复、区分过时决策与当前约束，并最终以私有测试验收代码**。它把“能解决题目”与“能像工程同事一样交付”区分开来。

**3 条核心要点：**

1. **把需求获取变成可测量的工程任务。** 基准包含 **101 个任务、101 个真实仓库、11 种语言、12 个应用领域**，每个任务配有 **26 个模拟同事**，具有明确职责、局部知识和受控的回复规则。Agent 从简短交接开始，通过项目看板、版本化文档、聊天、MR 和 CI 找到需求，并使用关联到需求的私有 **F2P（fail-to-pass）/P2P（pass-to-pass）** 测试验收；模拟同事并不等同于真实人类团队。
2. **通过部分测试不代表完整交付。** 对 **11 个模型**的评测，Claude Opus 5.5 和 GPT-6 Astra 分别通过 **63.84% / 62.91% 的 F2P 测试节点**，但完整任务成功率仅 **6.93% / 7.92%**。给模型直接提供完整需求的 Oracle-Spec 条件下，GPT-6 Astra 的 F2P 从 **62.91% 提升至 78.84%**，完整任务成功率却仍为 **7.92%**。这说明失败不只发生在“没有问清需求”，还发生在实现、验证与交接的后半程。
3. **记录了需求在长链路中如何丢失。** Claude Opus 5.5 在相关看板问题的首次询问中，平均 **93%** 找对负责人，但仅获取 **64%** 的同事掌握的需求；**450 条延期答复中 153 条没有继续跟进**。即使 Agent 在最终交接中宣称某项需求“已完成”，其中仍有 **31%** 未通过关联测试。作者借助需求→对话→修改→测试→交接的追踪关系，区分未取得、取得却未实现以及错误声称完成的情况。

> **核心启示：** 组织级 Coding Agent 需要一份可持续更新的 **Requirement Ledger**：每项需求记录来源、负责人、当前版本、未答问题、实现证据、测试结果和交接状态，而不是仅在起始 Prompt 中复制需求说明。

## 2. Synapse: Optimizing Natural-Language Agent Skills through Program Repair

- **作者/来源：** Lijuan Li（南京大学）、Zhenpeng Chen（清华大学）、Chenxi Zhang（西安电子科技大学）、Yihao Huang（华东师范大学）、Yang Liu、Chong Wang（南洋理工大学）/ arXiv 研究预印本
- **首次提交：** 2026-11-16 10:29:36 UTC（北京时间 2026-11-16 18:29）
- **arXiv 原文：** https://arxiv.org/abs/2611.20856
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.20856
- **相关技术：** Agent Skills、SKILL.md、SkIR、CFG/PDG、Source Mapping、Program Repair、Regression Test Selection

**推荐理由：** Skill 是自然语言文档，执行失败时往往只知道“结果错了”，却不知道该修改哪一段指令、哪条条件依赖受影响，以及修复是否让原本成功的任务退化。Synapse 借用编译器与程序修复技术，让 Skill 具备**部分 IR、源位置映射、依赖分析、受类型约束的补丁与回归筛选**。它尤其值得从 LLVM/MLIR、编译器 Pass 和测试选择的角度阅读：不是把 Skill 变成完全可执行语言，而是为其提取足够可靠的结构化视图。

**3 条核心要点：**

1. **Skill 的部分程序视图 SkIR，连接自然语言与程序分析。** 确定性编译器按类似 island grammar 的方式识别 Markdown Skill 中的操作、条件与数据引用，构建带有源码位置的 **SkIR**，导出控制流与程序依赖关系；未识别的其他自然语言要求仍留在原文中，继续交给 LLM 解释。因此这不是对所有自然语言含义的正确编译，也不能静态证明 Agent 会依照指令执行。
2. **按程序修复流程定点修改并回归测试。** 系统从执行轨迹定位疑似指令，把相关条件及依赖提供给修复模型；模型只能提出类型化 SkIR 变更，Host 将变更写回对应源码片段并重新编译，再利用覆盖关系、CFG/依赖边选择包括历史成功用例在内的测试。接纳补丁要求其通过筛选并改善独立验证集表现。**未修改的指令源码片段保持不变**是 Host 可检查的性质；测试选择覆盖所有潜在受影响任务则依赖论文的 *one-hop-local* 执行假设。
3. **六组受控实验有效，但还不是复杂代码代理的端到端证明。** 在 **DocVQA 与 LiveMath** 两个单轮问答基准、三个执行模型的六组设置中，Synapse 都优于 SkillOpt、Trace2Skill 和 SkillBoost；相对 SkillOpt，DocVQA 成功率提高 **3.74–4.54 个百分点**，LiveMath 提高 **2.40–4.00 个百分点**。两次 DocVQA 修复运行的 **37 个补丁里有 23 个**通过控制流/依赖关系额外选中了测试，其中一个额外测试发现仅看被编辑指令覆盖率会漏掉的回归。实验证明了方法潜力，**没有直接验证多工具、长期运行的生产 Coding Agent Skill**。

> **核心启示：** 把 Skill 当作可维护的工程资产：`Markdown Skill → Partial IR + Source Map → Fault Localization → Typed Patch → Regression Selection → Validation`。与其让 Agent 每次整篇重写规则，不如逐条修复并保存可追溯的补丁和失败案例。

## 今日思考

两篇文章讨论的是 Software Factory 中两种容易失真的“规范”：**外部需求与内部执行知识**。SWE-CoWork 显示需求即使已经被告知 Agent，也可能在实现和最终交接之间遗失；Synapse 显示 Skill 即使修好一个失败案例，也可能牵连其他原本正确的行为。

一个值得实验的组合是：

**Versioned Requirement Ledger → Requirement-to-Test Traceability → Versioned Skills / SkIR → Targeted Repair → Regression Suite → Independent Acceptance → Evidence-Based Handoff。**

这里需要保持两条独立的证据链：需求是否来自正确的负责人、仍然有效；Skill 的修改是否局限于预期位置、通过既有与新增测试。不能用 Agent 自己的“完成”表述替代任意一条链路的验收。

**值得追问：** 当 PR 依赖跨团队多轮澄清时，如何自动检测延期答复未跟进？当 Skill 的部分 IR 无法识别重要自然语言约束时，如何让回归测试不因静态依赖图不完整而漏测？两篇研究的基准和实验环境不同，以上组合是可验证的工程假设，**不是两篇论文已联合验证的生产架构**。

**证据边界：** 两篇的作者、首次提交时间和主要指标已按 arXiv 元数据及对应论文正文核对；AlphaXiv 的对应论文内容由文献连接读取核实，标准网页 URL 的独立 HTTP 访问未成功。SWE-CoWork 依赖模拟同事与作者设计的私有测试，Synapse 依赖 DocVQA/LiveMath、部分语法提取和 one-hop-local 假设，均需更多独立验证。
