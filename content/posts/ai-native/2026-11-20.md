今天选择两篇**过去七天内首次公开的原创研究**：一篇研究怎样让 Coding Agent 的 Harness 按用户显性和隐性需求迭代；另一篇研究怎样让 Agent 自动生产贴近企业代码的评测基准，并识别容易误导工程决策的坏基准。两者把「系统如何演化」与「改进如何被可靠测量」连接起来。

共同问题：**Harness 的更新为什么不能只看 benchmark 分数，以及用于衡量更新的 benchmark 本身如何接受独立检验？** 两篇都是研究预印本；报告的性能数字来自作者实验，尚未独立复现。

## 1. Agentic Harness Engineering Beta: Requirement-Centered Evolution of Agent Harnesses

- **作者/来源：** Jiahang Lin、Jiahao Chen、Yiding Wang、Shichun Liu、Chengjun Pan、Shihan Dou 等（共 14 位作者）/ 复旦大学、北京大学、中国人民大学等；arXiv 研究预印本
- **首次提交：** 2026-11-18 18:52:13 UTC（北京时间 2026-11-19 02:52）
- **arXiv 原文：** https://arxiv.org/abs/2611.24924
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.24924
- **相关技术：** Coding Agent、Harness Evolution、Implicit Requirements、User Simulation、Gitea、RFC/PR、Human Evaluation

**推荐理由：** 传统自动 Harness 优化往往使用任务 verifier 或单一 benchmark 分数挑选代码变更，容易把一次性补丁误当成通用改进，也难发现用户没有明说的交互需求。AHE-Beta 把多轮模拟用户反馈转换成跨任务的需求，在 Gitea 中完成归纳、设计、代码审查和合并；**Harness 的演化按需求证据决定，而 benchmark 只在演化后评价**。这比单纯自动搜索 Prompt 更接近真实工具链产品的版本迭代。

**3 条核心要点：**

1. **让用户交互产生可追溯需求。** AHE-Beta 用覆盖七类偏好维度的 **50 个模拟用户画像**与 Harness 多轮交互；模拟用户从可见回复、进度与操作中提出 Issue 并评分，能暴露任务最终测试不覆盖的范围控制、中途纠正、进度反馈与证据呈现等隐性需求。模拟用户只看到用户界面，不直接读取 Harness 内部实现；它们仍不能代表所有真实使用者。
2. **把 Harness 自我修改变成团队化开发。** Gitea 中由 **Triage → Architect/PM → Developers** 分工：过滤任务特定或无效 Issue，跨会话归纳共同根因和未明说的要求，编写 PRD/RFC，拆分实现任务，审查 PR。只有与已核实需求相连并通过评审的修改才合并；**演化期间不按 benchmark 得分挑选补丁**，从制度上限制为单个测试样本投机改写。
3. **独立任务与真人对照验证收益及边界。** 在作者保留的任务上，相比 Base Harness，**pass@1 从 21.9% 升至 33.3%，Token 用量减少 40.8%**；盲测真人 A/B 的 **48 个有效配对中有 31 个偏好 AHE-Beta**，五项评分维度方向均更高。不再演化直接迁移至 GLM-5.3 与 DeepSeek-V4.1-Flash 时，pass@1 分别高 **15.8 和 5.3 个百分点**。这些是特定 Harness、任务、模型和评价设置的研究结果，不等于任何项目自动升级都能获得相同收益。

> **核心启示：** Harness 的 PR 应当能回溯到原始会话、用户需求、实现 RFC 和验收证据；「指标提升」是观察结果，而不是修改获得合并资格的唯一理由。

## 2. Benchmark Factory: Agentic Benchmark Creation via Dataset Curation and Label-Free Quality Anchors

- **作者/来源：** Shervin Shahidi、James Poon、Hang Xie、Kenneth O. Xu、Robin Håkanson、Vikram Nair、Jens Pillgram-Larsen、Nachiappan Nagappan / Meta Platforms；arXiv 研究预印本
- **首次提交：** 2026-11-13 19:49:01 UTC（北京时间 2026-11-14 03:49）
- **arXiv 原文：** https://arxiv.org/abs/2611.18890
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.18890
- **相关技术：** Coding Agent Eval、Benchmark Factory、Merged Code Changes、Meta-Agent、Label-Free Quality Anchors、Holdout、Human Review

**推荐理由：** Coding Agent 在具体组织里需要针对本仓库的 Eval，但从已合并的生产补丁自动生成任务，容易混入过难、过易、描述不完整或评分器失真的题目。Meta 的 Benchmark Factory 将建题本身变成 **元代理的迭代工作流**，引入无需逐题人工标签的模型能力排序、难度区间和对照规则，同时保留冻结评分准则、独立测试和人类验收，重点不是追求更大的题库，而是避免错误基准对模型选型产生虚假信号。

**3 条核心要点：**

1. **从真实代码变更自动制造并修复评测集。** 元代理从已合并的生产变更写取样查询，把 Agent 放在变更前 Commit 上实现任务，运行已知能力层级的模型，检查难度、模型排序及运行稳定性等 **quality anchors**；未满足时优先调整任务来源和呈现，而非任意重写评分器或预设能力排序。任务取样和配置在修复子集上调整，另留 holdout 检查泛化；证据不足或反复失败则交给人工。
2. **独立模型与推理力度对照检验可迁移性。** 作者为 **五个开发团队群组**建立基准；在基准构建时未参与选择的模型与设置上，**GPT-5.5 对 GPT-5.4 的通过率为 65.8% 对 60.5%（p=0.004）**，Claude Opus 4.7 的高、低推理力度为 **60.6% 对 54.4%（p=0.002）**。这说明已接受的基准在所测对照中保留了合理区分能力，**不能证明这些基准测量的是全部真实工程质量**。
3. **负对照与人工审核揭示锚点的边界。** 约 **5% 的任务人工抽检（30 题）**得到平均任务质量 **2.3/3**、评分判定质量 **2.6/3**；五个故意破坏的 grader 与一个刻意简单的基准被质量锚点拒绝，随机打乱模型标签后虚假通过的模拟比例至多 **1.4%**。然而抽检中的错误判定主要来自**任务描述缺少实际合并补丁中的必要细节**，且部分题目依赖 LLM grader；锚点是必要条件，不是正确性或公平性的充分保证。

> **核心启示：** 自动产生的 Eval 必须同时留下任务来源、评分器版本、受控修复历史、独立 holdout、负对照与人工审计结果；只看模型分数排序仍可能选中有系统性偏差的基准。

## 今日思考

两篇论文正好构成一个 AI-native Software Factory 的双向约束：

**用户交互 / 隐性需求 → Requirement Ledger → RFC / PR → 独立验收 → Harness 新版本**

**真实已合并变更 → 自动基准生成 → 质量锚点 / Holdout / 负对照 → 人工审计 → 稳定评测资产**

值得验证的工程假设：**让 Harness 变更与其对应 Eval 都具备可回溯的证据链、独立冻结的验收条件，而不是让同一个优化 Agent 同时改系统、改题目、改评分器。** AHE-Beta 的用户满意度与 Benchmark Factory 的统计排序分别提供了不同层面的证据，不能相互替代。

**证据边界：** AHE-Beta 使用受控任务、模拟用户和有限真人 A/B，移植不同组织需验证交互画像、任务集与审查流程；Benchmark Factory 在 Meta 的五类内部开发群组上评估，并非公开跨企业普适基准，抽检规模较小且有 LLM grader 判断误差。两篇 arXiv 的标题、作者、首次提交日期已从 arXiv 核对，AlphaXiv 对应论文全文通过文献连接核对，但两篇 AlphaXiv 标准网页独立 HTTP 抓取失败。所有数值为论文作者报告，尚未独立复现。
