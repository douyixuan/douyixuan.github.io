今天的两篇原创资料分别讨论 **Agent 的长期经验能否转化为能力**，以及 **当大量 Agent 同时产出代码时，基础设施如何扩容**。

## 1. FrontierMemory 1.0: Benchmarking continual learning through memory

- **作者/来源：** Letta Research / FrontierMemory
- **发布日期：** 2026-10-21（第三方发布记录；原作者页面只标注 2026 年 10 月，未标明确切日期）
- **原文：** https://www.frontiermemory.com/blog/v1/

**推荐理由：** 传统 Agent Memory 测试多是从历史对话中找答案，不能直接证明 Agent 会因经验而完成原本做不好的工作。FrontierMemory 把历史轨迹、可提炼的记忆和下游可执行任务连起来，提供更接近长期 Coding Agent 的评测思路。它还比较模型与原生 Harness 的记忆生成效果，明确展示失败案例和评测局限。

**3 条核心要点：**

1. **衡量经验迁移，而非事实回忆。** 基准从现有编码和知识工作任务中构造 15 个依赖历史经验的任务，区分任务规则、用户偏好和环境知识三种记忆。评测者提供 665 条先前轨迹，其中仅 219 条与目标任务有关；每个任务另有供确认任务可解的标准记忆（gold memory）。
2. **记忆质量要由下游任务验收。** Letta 发现原始候选任务中有 53% 存在不可靠的校验器，并进行了修复。同一套 15 任务、固定任务模型的对照中，Opus 5.5 配合 Letta Dream/Letta Code 的全通过率为 73.3%，配合 Claude Managed Agents 的结果为 33.3%；这些数字来自作者自己的小规模评测，且不同方案同时改变了记忆机制与 Harness，不能直接推导普适排名。
3. **可执行的经验指令比流水账更有用。** 定性分析发现，写明“何时使用某项技能”的指令更容易被下游 Agent 加载；把偶然的文件大小、路径等细节记成规则，则容易对历史轨迹过拟合，在新任务上失效。作者还观察到优质记忆能跨任务执行模型迁移；当前版本仅覆盖离线回顾（dreaming），不验证持续在线学习。

> **核心启示：** Memory Eval 应检查 `Past Trajectories → Learned General Rules → New Task → External Verifier` 的全链路，而不是只问 Agent 是否记得某条历史事实。

## 2. The bridge to agent-scale Git infrastructure

- **作者/来源：** Eleanor White、Victoria Dye / GitHub Engineering
- **发布日期：** 2026-10-21
- **原文：** https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/

**推荐理由：** 当 Coding Agent 持续创建分支、提交和运行 CI，原来按人类开发节奏设计的 Git 存储系统会遇到新的写入与读取规模。GitHub 不是只增加服务器，而是在迁移生产仓库的同时调整并发控制粒度，并准备让读取节点独立扩容。这篇是有真实线上约束和内部性能测试的工程复盘。

**3 条核心要点：**

1. **Agent 流量让基础设施迁移变成线上容量问题。** GitHub 报告已有 99.99999% 的仓库同时在自有数据中心和 Azure 存有副本，Azure 承担约一半 Git 流量。剩余极高活跃仓库受跨区域约 25ms 往返延迟影响：过去整个仓库的写入锁会一直等最慢的健康副本，使并发 Push 排队。
2. **从仓库级锁变为引用级串行化。** Git 的强一致性主要要求同一 branch/tag 引用的更新保持先后关系；不同引用之间的大部分写入可并行。GitHub 将 quorum 的串行化粒度改为单个 ref，使 Agent 在不同分支上的写入无需互相阻塞；文章报告内部真实流量测试中，不同引用写入吞吐量提高约 3–4 倍。这是内部测试结果，不等于所有仓库都已完成该架构切换。
3. **把持久存储、写入仲裁、弹性读取拆开。** 新方案引入以 Azure Blob Storage 为持久底座的虚拟写副本，并规划按需扩展无持久状态的虚拟读副本。对象写入先满足持久性再确认；读取节点从对象存储预热缓存。作者同时强调后台状态追赶、强一致读以及后续写入吞吐量仍有待继续解决。

> **核心启示：** Agent-scale Infrastructure 需要 `Per-ref Concurrency → Durable Object Storage → Independent Read Scaling`，而不是假设单仓库写入和完整本地 Checkout 永远是合理的工作单元。

## 今日思考

**Agent 的“经验”与“吞吐”是两个不同的系统问题。** FrontierMemory 提醒我们：更多历史记录不等于持续学习，必须用新的外部任务验证经验是否迁移成功；GitHub 的实践则表明：即使 Agent 真能高效执行，源代码平台也需要重新审视锁粒度、数据复制和无状态计算的边界。

两者的共同原则是：不要依赖表面代理指标（检索命中、工具调用成功、提交数量），而应把可验证的下游结果作为优化目标。
