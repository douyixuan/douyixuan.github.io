## 1. AI R&D-relevant model capabilities are improving rapidly and are getting harder to measure

- **作者/来源：** Megan Kinniment、Manish Shetty、Brian Goodrich 等 11 位贡献者 / METR
- **发布日期：** 2026-11-20
- **原文：** https://metr.org/blog/2026-11-20-q4-2026-capability-update/
- **相关技术：** Agent Evaluation、Time Horizon、Human Baseline、Lifecycle Cost

**推荐理由：** 这份独立评测更新不仅给出能力增长趋势，还分析了自动评分与训练环境相似、专家基线难获取、缺少快速反馈等测量困难。设计 Coding Agent 的 Eval 时值得关注这些限制。

**3 条核心要点：**

1. **分开评价执行与判断。** TH1.1 有 222 项任务，TH2 有 36 项任务、12 个任务族，其中 8 个族偏可验证，4 个族偏难验证或专家判断。在有明确反馈的编码与优化任务上模型表现很强，但在反馈不足时，其判断力仍可能弱于领域专家。
2. **评测成本也是难度信号。** 控制人类任务耗时后，估算的评测生命周期成本翻倍，对应的代理任务时长能力大约减半。这是样本上的经验关系，不是因果定律。新的专家基线很难收集，仅 9% 的人类完成时间估计直接使用实际人类基线。
3. **谨慎使用增长曲线。** 合并 TH1.1 与 TH2 后，估计任务时长能力约每 3.6 个月翻倍；多代理并行在反馈迅速、目标明确的任务中更有希望，在其他任务中的收益不确定或为负。不能将这一趋势直接外推成开放式研发的自动化进度。

> **核心启示：** Eval 应保留真实任务的反馈约束，并把可执行评分与专家判断分别测量。

## 2. Maintainers don't need more AI bug reports. They need fixes.

- **作者/来源：** Ashley Wolf、Gregg Cochran / GitHub Blog
- **发布日期：** 2026-11-17
- **原文：** https://github.blog/open-source/maintainers/maintainers-dont-need-more-ai-bug-reports-they-need-fixes/
- **相关技术：** Agentic Workflow、AI Triage、Independent Review、Private Vulnerability Reporting

**推荐理由：** GitHub 与 Microsoft 的 MDASH 试点展示了真实开源维护流程如何消化 AI 发现，而不把筛选负担转移给维护者。它将发现、审核、建议补丁、实际修复和发布区分为不同阶段。

**3 条核心要点：**

1. **发现不是交付。** 六个开源项目共收到系统产生的 9,791 个潜在线索，经过 Copilot 技能驱动的筛选和研究人员逐项核验后，只有 99 份附有建议修复的报告私下交给维护者。该比例不是模型准确率。
2. **以真实修复衡量成果。** 截至 11 月 15 日，维护者已经修复 55 项，其中 14 项进入正式版本；是否采用或修改建议补丁由维护者决定。这是阶段性结果，不能将未修复项视为无效发现。
3. **验证能力仍是瓶颈。** 七位研究人员平均每个项目约花两天进行人工核验；私有协作、隔离测试和维护者自主决定发布时机仍然重要。六项目试点不能证明整套过程可以无人值守地规模化。

> **核心启示：** 不用发现量衡量代理交付，把核实后的报告、合入修复与正式发布分别记录。

## 今日思考

METR 的评测结果与 MDASH 的生产试点揭示了同一个问题：容易自动生成或评分的中间结果，并不能代表真实工程价值。可以将软件工厂的验收拆成 **Candidate → Independent Evidence → Expert Review → Merged Fix → Released Fix**，分别统计通过率和人工时间，并保留难验证任务作为独立评测集。这是建议验证的工程设计，不是两篇文章已经联合证明的方案。

**证据边界：** METR 的趋势取决于任务集、模型、预算及基线估计；MDASH 为组织自报的小规模试点。两篇均为原创网页文章，不是 arXiv 论文。
