今天选择两篇过去七天的原创内容：**2026 年 11 月 10 日**的 Google DeepMind 技术报告与 **11 月 4 日**的 Thoughtworks 工程方法论。前者回答「多代理写出的海量证明怎样不依赖模型的自我保证」，后者回答「当多个团队都开始用 Agent，怎样保证它们理解同一套目标与完成条件」。二者的共同切入点是**可审查的规格与独立的工程约束**，但证据类型不同：一篇提供可供复核的形式化成果，另一篇提供实践归纳而非受控实验。

## 1. AlphaProof Code: Verifying Signal’s Security at the Machine-Code Level

- **作者/来源：** Swarat Chaudhuri、Andrew Ferraiuolo、Anton Kovsharov 等 / Google DeepMind、Google
- **发布日期：** 2026-11-10
- **原文（技术报告 PDF）：** https://deepmind.google/documents/36/Formal_Verification_of_Signal_4.pdf
- **官方导读：** https://deepmind.google/blog/introducing-alphaproof-code/
- **形式化成果与规格：** https://google-deepmind.github.io/code-verification/
- **相关技术：** Coding Agents、Lean、AArch64 ISA Semantics、libsignal、PQXDH、Triple Ratchet、Formal Verification

**推荐理由：** 这不是「让模型生成一段验证代码」的演示。团队把**未经修改的 Rust 密码协议实现**用标准编译器编成 AArch64 代码，对批准后的安全规格生成并机器检查大规模证明。论文细化了多代理角色、共享代码冲突处理、规格审批、可信计算基和验证器边界；对 Compiler / GPU Toolchain 工程师尤其值得看的是**从源码到机器语义的证明链**如何避免把编译后的执行行为想当然地等同于源代码。

**3 条核心要点：**

1. **验证跨过源代码与抽象协议的界限，但有明确覆盖范围。** 研究将 `libsignal` / `spqr` 的未修改 Rust 代码编译为 AArch64 Linux 可执行程序，在 Lean 的机器语义中证明 **PQXDH 握手与 Triple Ratchet** 的关键性质，包括前向保密、认证、失陷后安全等。它验证的是特定机器语义、执行模型和外部加密原语契约下的性质，**不是整个 Signal App、所有平台和所有部署配置已被证明安全**。
2. **证明可以高度并行，规格却必须保持受控。** 团队产出约 **650 万行** Lean 证明，建立在约 **2.6 万行**可信规格及 AArch64 语义之上。论文披露典型证明团队有 **40–80 个代理**，通过 Orchestrator、Team Lead、Proof Worker、Architect 和 Integrator 分工；同一文件同时仅由一个 Worker 编辑，只有 Integrator 提交。人类审核规格，Agent 只能提出带证据的修正规格建议，不能为了证明通过而自行改写验收目标。
3. **用与生成者分离的机器检查器防止“证明成功”的假象。** Gatekeeper 要求 Lean Kernel 检查证明，并核对证明的命题恰好对应**预先保留的批准规格**；模型输出本身不被信任。研究还把两个历史上已修复的真实漏洞重新引入隔离版本，验证相应安全定理在有缺陷的二进制上不成立。可信边界仍包括规格正确性、Lean Kernel、AArch64 语义及部分外部函数/密码原语假设；其单线程、静态链接的模型也不能直接覆盖所有程序行为。

> **核心启示：** `Human-reviewed Spec → Unmodified Source → Compiler / Machine Semantics → Parallel Proof Agents → Independent Lean Check`。把 Agent 的大规模输出变成可复核成果，关键不是再安排一个模型说「通过」，而是由**独立、范围清晰的检查器**验证不可随意修改的规格。

## 2. Macro trends in the tech industry — November 2026

- **作者/来源：** Chris Ford / Thoughtworks（Technology Radar Vol. 35 相关工程分析）
- **发布日期：** 2026-11-04
- **原文：** https://www.thoughtworks.com/insights/blog/technology-strategy/macro-trends-tech-industry-november-2026
- **相关技术：** Agent Harness、Progressive Context Disclosure、Enterprise Harness、Model Routing、Agent Sandboxing、Software Factory

**推荐理由：** 单个工程师能靠隐性知识让 Coding Agent 完成任务，但当项目与团队增加，约束不一致、审查排队、Token 账单和工具权限就成为新的瓶颈。Chris Ford 依据 Thoughtworks 的 Technology Radar 与工程观察，给出一套有取舍的组织方法：**从共享上下文、任务验收到 Harness 归属，把 Agent 能力做成有负责人和服务承诺的平台**。这属于观点和实践总结，不应当被读成有量化对照的生产率研究。

**3 条核心要点：**

1. **首先规模化的是共同理解，而不只是上下文窗口。** 不同团队必须共享「什么算完成」、哪些约定具有强制性、哪个数据源可信。文章主张把 Context 当作有 Owner 的资产，使用 **Progressive Context Disclosure** 按需提供信息，并借助 OpenSpec、提前追问需求等方法将评审前移到 Spec；每个领域维护统一验收定义和 Eval，防止 Agent 各自理解一套任务。
2. **评价单位从 Token 和代码产量转到完成任务的全成本。** 在多模型 Router / Gateway 中管理预算、延迟和策略，考察 **Cost per Completed Task** 而非孤立 Token 单价；审查端用风险分层、Review WIP 上限、Cycle Time 与返工率衡量真实吞吐。大量生成代码不代表相同程度的有效交付，匆忙点过 PR 更不等于完成审查。
3. **Harness 应成为可运营的平台产品。** Context Assembly、Eval、Sandbox、Identity、权限、费用与可观察性不能长期分散为各团队的临时脚本。作者建议为共享 Harness 指定平台 Owner、Golden Path、SLO 和弃用策略；将 Agent 的权限、工具、依赖和 CI 纳入威胁建模。把这些能力当作平台维护，才能使多个团队在不重新发明安全与验收机制的情况下复用。

> **核心启示：** `Shared Context / Definition of Done → Versioned Harness → Task Execution → Risk-tiered Review → Outcome + Cost Measurement`。软件工厂的组织瓶颈不是模型不够快，而是团队没有共同规格、没有可靠验收，或没有人负责 Agent 运行环境。

## 今日思考

这两篇文章讨论同一条工程主线的两个尺度：

- **单项任务的可信度：** AlphaProof Code 将人类认可的安全命题冻结，由大量 Agent 并行构造证明，却只信任 Lean Kernel 对固定命题的检查结果。
- **跨团队的可扩展性：** Thoughtworks 要求团队在任务启动前约定上下文、验收集、权限和成本边界，并明确谁负责持续运营 Harness。

一个有用的抽象是：

**Shared Intent / Spec → Controlled Agent Harness → Executable Artifacts → Independent Validation → Human Ownership**

还值得追问：**当验证器本身包含模型、编译器语义或外部库假设时，哪些对象被证明了，哪些仍属于 Trusted Computing Base？当多团队共享 Harness 时，谁维护 Spec、Eval 和版本兼容性？** 这两个边界决定了「Agent 完成」的声明能否成为可以被他人信赖的工程结论。
