今天选取两篇本周原创工程文章（11 月 23 日、19 日）。主题是代理介入真实系统后，如何通过独立运行时约束、可审计证据和跨层观测控制风险。

## 1. OpenAI and Cisco introduce Shirudo

- **作者/来源：** OpenAI × Cisco（原文未单列个人作者）
- **发布日期：** 2026-11-23
- **原文：** https://openai.com/index/introducing-shirudo/
- **相关技术：** eBPF、Runtime Protection、TPM Attestation、Coding Agent

**推荐理由：** 与直接让 Coding Agent 修改并重启生产服务不同，Shirudo 将临时防护作为可测试、可签名、可批准的运行时制品，展示模型生成代码与确定性执行环境之间的职责划分。

**3 条核心要点：**

1. **临时防护与正式补丁分离。** eBPF shield 可以在不中断应用的情况下约束特定行为，先观察正常负载影响，再决定是否启用强制保护。它是等待永久修复期间的风险缓解措施，不替代补丁。
2. **独立验证和授权。** Agent 可以提出和验证候选防护，但部署由操作者控制。签名、内核 eBPF verifier 和访问控制约束加载；TPM 支持记录防护的加载与移除。内核 verifier 检查程序安全规则，并不证明业务语义正确。
3. **从受控演示到生产仍有距离。** 发布方报告 Codex 生成的 shield 在实验中阻止针对运行中 Elasticsearch 的漏洞利用，无需重启服务。文章没有提供跨生产负载的全面误阻率、性能开销或通用有效性验证。

> **核心启示：** 将 Agent 的候选修改和真正拥有运行时执行权的系统分开，并保留可独立核验的部署记录。

## 2. An AI Observability Framework for Your Agentic Applications

- **作者/来源：** Raviteja Sunkavalli、Matheus Arrais / AWS Cloud Operations Blog
- **发布日期：** 2026-11-19
- **原文：** https://aws.amazon.com/blogs/mt/an-ai-observability-framework-for-your-agentic-applications/
- **相关技术：** OpenTelemetry、OpenInference、Agent Tracing、Regression Eval

**推荐理由：** 传统健康检查很难发现代理输出错误、上下文压缩丢失约束或虚报完成。文章提出一套可作为 Agent Harness 设计检查表的跨层观测方法。

**3 条核心要点：**

1. **四层三维观测矩阵。** 将应用、代理执行、模型、基础设施分别按质量与可靠性、费用、安全与治理检查。以共享 trace ID 关联工具调用、检索、模型版本、批准事件及底层服务；不把 API 成功当作任务成功。
2. **从开发期建立回归闭环。** 从第一版记录轨迹，以真实任务和经人工校准的评估器检查路径及结果；Prompt、模型、工具、Harness 的变更经过 CI Eval，生产抽样失败加入回归集，并设置步数和费用上限。
3. **关联根因并保护遥测。** 使用 OpenTelemetry GenAI 语义约定连接各层，观察模型等待、缓存命中、GPU/KV cache、会话恢复和工具重复等信号；对日志脱敏并限制保留期限和访问权限。该框架是工程建议，不是经过对照实验验证的性能提升结论。

> **核心启示：** 把任务成功、执行轨迹、费用与授权证据放在同一条可查询的链路上。

## 今日思考

两篇文章分别从控制面和观测面说明：Agent 生成的动作不能自动取得真实系统执行权，执行结果也不能仅凭代理自述确认。值得验证的工程设计是 **Candidate → Isolated Validation → Approval → Signed Deployment → Correlated Telemetry → Regression Eval**。其中运行时权限、验证器和遥测采集应具有独立于生成模型的约束。

**证据边界：** Shirudo 为发布方的受控演示和开源项目介绍；AWS 为参考框架，未提供该框架的因果收益实验。两篇均为原创网页文章，不涉及 arXiv 论文。
