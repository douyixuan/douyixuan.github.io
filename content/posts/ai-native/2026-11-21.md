今天选择两篇**过去七天内首次公开的研究预印本**。第一篇把真实世界 Agent 事故变成可重放、可对照的自动审计用例；第二篇量化 Agent 长时间等待模型时，云端隔离运行环境造成的会话容量占用。共同问题是：**既要让 Agent 在真实环境中不造成破坏，也要看清为其提供隔离所付出的运行时资源代价。**

两篇发表于 2026-11-19 UTC；论文结果来自作者实验，尚未独立复现。下列 arXiv 元数据与论文内容已核对，AlphaXiv 对应论文文本已通过文献连接读取；AlphaXiv 标准页面的独立 HTTP 访问暂未成功。

## 1. Replication of Agentic Security Events: Audit and Investigation (ROGUE-AI)

- **作者/来源：** Mengxiao Wang、Mahbub Alam、Kalyan Nakka、Nitesh Saxena / Texas A&M University；arXiv 研究预印本
- **首次提交：** 2026-11-19 18:23:35 UTC（北京时间 2026-11-20 02:23）
- **arXiv 原文：** https://arxiv.org/abs/2611.26553
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.26553
- **研究材料：** https://rogue-ai.surge.sh
- **相关技术：** Agent Security、Incident Replication、Counterfactual Control、Multi-Agent Evaluation、Tool-Output Warning

**推荐理由：** 既有 Agent 安全基准通常给定人工设计的攻击与任务，难以解释公开事故为什么发生。ROGUE-AI 将事故报道当作待检验的因果主张，构造**唯一移除被指认危险因素的匹配对照**，让当前 Agent 在两种环境中重新决策，再由代码根据环境状态判断是否造成实际危害。它把事故复盘升级成可回归执行的 Agent Runtime 验收资产。

**3 条核心要点：**

1. **把事故报告编译成受控复现。** 专业 Agent 从 **253 份报告**中筛选证据和事故原因，构造 **108 组复现，对应 96 起事故、38 类事件**。跨厂商审查者检查场景保真，程序状态检查器而非被测 Agent 的自述判断危害；控制组仅移除例如「测试连接到生产数据库」的危险因素。不能由离线重建直接证明原事故的全部细节。
2. **真实风险常不需要攻击者。** 作者报告 **108 次尝试中 89%** 再现了报告描述的危害；五种模型在事故环境中 **18%–33%** 的运行重犯问题，对照组至多 **1%**。在 **72 起实际伤害事故中有 62 起无攻击者**：Agent 遵循表面任务，却忽视生产凭据、共享数据库等环境危险。该比率只适用于选入论文的事故与复现环境，不代表任意部署的事故发生率。
3. **具体危险提示优于空泛规则。** 在工具输出后附加**明确指出危险及后果**的警告，可降低五个模型的危害发生率；同长度但不点明危险的提示效果明显较差。论文还比较用户确认、数据流追踪等防护；提示不是权限隔离或危险工具审批的替代品。

> **核心启示：** 把事故原因编码为 `Incident Environment / Matched Control / State Oracle`，每次升级模型、Harness 或工具权限都可重新审计，且在危险工具调用前显示具体的环境后果。

## 2. Held While Waiting: What LLM Agent Sessions Reserve on Serverless and Agent Runtimes

- **作者/来源：** Mekhala Hithyshini Sreenivasa；arXiv 研究预印本
- **首次提交：** 2026-11-19 17:40:09 UTC（北京时间 2026-11-20 01:40）
- **arXiv 原文：** https://arxiv.org/abs/2611.26480
- **AlphaXiv：** https://www.alphaxiv.org/abs/2611.26480
- **相关技术：** Agent Runtime、AWS Bedrock AgentCore、LangGraph、Strands、Serverless、Per-Session Isolation、Capacity Planning

**推荐理由：** 模型等待时间往往远超 Harness 的本地 CPU 工作，但为安全隔离分配的运行环境仍可能被整个会话占住。论文用独立 CPU/网络测量、实际 Agent 轨迹和容量仿真，区别了**Token 费用、CPU 账单、预留环境数量与会话隔离**，揭示低 CPU 费用不等于高并发承载能力。

**3 条核心要点：**

1. **分开测量等待和 CPU，避免错误微基准。** 在包含 **384 个会话、3,549 个 warm steps** 的部署数据中，模型调用等待中位约 **2.7 秒**，单步 Framework CPU 估计仅 **5–40 毫秒**。作者保留模型客户端序列化过程，只模拟底层网络，并在不同机器和 AgentCore/Lambda 中测量；直接把模型对象替换为 Stub 会漏计随历史增长的序列化开销。
2. **会话隔离占的是容量，而不只是计费。** 按论文所测 AgentCore 行为，每个会话独占隔离运行环境，结束后若客户端不主动关闭，可继续保留到 **15 分钟空闲超时**。在平均 **33 秒** 的客服会话案例中，与及时关闭相比，依赖超时会令同时预留的环境数约扩大 **28 倍**。AgentCore 在 I/O 等待期不计 CPU 费用，但预留环境仍消耗容量/配额；这些是论文观察到的服务条件，而不是所有平台的通则。
3. **共享能提高容量，但有隔离前提。** 按实测负载驱动的**模拟**，每环境共享 **64 个会话**，预留环境数减少约 **59 倍**，99% 的回复额外等待不超过 **40 毫秒**；**这不是实际 AgentCore 已提供的 59 倍优化**。共享需要云平台支持，且必须解决不可信工具或模型生成代码在多会话间的强隔离问题。

> **核心启示：** 高并发 Agent 平台先验证及时关闭、空闲超时和会话配额；进一步研究隔离执行与共享等待环境的分层，不要为省容量默认把不可信会话放进同一进程。

## 今日思考

两篇论文揭示了同一个运行时设计张力：

**真实事故 → 离线复现 / 匹配对照 / 状态判定 → 危险识别与回归验收**

**运行轨迹 → 等待与 CPU 分离测量 → 会话容量模型 → 关闭策略 / 安全隔离**

值得试验：给 Agent Harness 增加「环境危险声明 + 有副作用工具的可重放回归」；给 Runtime 增加「Session 创建/关闭、空闲环境、配额、Token 与 CPU」四类独立指标。**性能优化不能牺牲会话级权限边界，安全警告也不能代替独立状态验证**。这是组合工程建议，尚非两篇论文联合验证的结论。

**证据边界：** ROGUE-AI 根据公开报道离线重建事故，不拥有原始生产日志，所谓复现是对重建场景与原因主张的实验支持；其安全收益仍需在真实系统中检验。Held While Waiting 的 CPU 数字部分来自受控测量及估计，59 倍来自共享模拟；云平台行为和配额可能随版本变化。两篇均为未经独立复现的研究预印本。
