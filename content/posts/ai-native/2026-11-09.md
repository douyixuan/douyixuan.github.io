今天选择两篇 **2026 年 11 月 5 日**发布的原创工程实践，分别处理 Agent 执行权的两个层面：Dropbox 将能运行任意现有软件的**文件操作 Agent** 放进与凭证隔离的工作空间，并在外部授权、追踪和撤销；Tobias Zimmergren 把**编程代理的命令规范**从模型可忽略的文字，升级为由 Harness 检查的权限和 Hook。共同问题不是「怎样提示 Agent 更听话」，而是：**当它真的发起操作时，谁有能力拒绝、记录并恢复？**

## 1. How two engineer side projects became the agent taking action inside Dropbox

- **作者/来源：** Daniel Reiter Horn、Rich Chan / Dropbox Tech
- **发布日期：** 2026-11-05
- **原文：** https://dropbox.tech/machine-learning/how-two-engineer-side-projects-became-the-agent-taking-action-inside-dropbox
- **相关技术：** Codex App Server API、JSON-RPC/JSONL、QEMU、Riviera、rclone、Pi Harness

**推荐理由：** 这是把 Coding Agent 从「修改代码」扩展到「修改用户真实文件」的具体产品架构，而非概念性演示。作者交代了工具运行环境、界面事件协议、凭证隔离、授权通道、启动开销和跨会话撤销的实际设计取舍；对于具备文件读写能力的 AI-native 产品，最值得研究的是**独立于 Agent 的执行边界**。

**3 条核心要点：**

1. **解耦 Agent Harness、界面和授权层。** 界面消费 Codex App Server 的结构化 JSON-RPC/JSONL 事件，按 thread / turn / item 组织对话、命令、计划和文件变更；Pi 可通过适配器映射到同一协议。面对模糊请求，先让用户批准计划，再按文件夹申请 Allow / Deny 访问权。即使更换 Agent Harness，真正授予文件访问权限的仍是外部可信宿主，而非模型自行决定。
2. **让沙箱拥有工具，但不拥有凭证。** Dropbox 借用 Riviera 的 QEMU 内存快照，为每段会话启动 Ubuntu VM；使用 rclone 提供文件操作视图。VM 不具备通用互联网访问；请求经代理转发到 VM 外的 `host_tools`，先检查目标、操作和用户授权，再附加服务凭证。这条检查链覆盖工具调用与 VM 内软件产生的文件访问。作者报告，在其测试中 **75% 的工作空间在启动请求后 300 毫秒内已连接 Dropbox、可发送第一条模型请求**；该数字不是端到端任务时延。
3. **把撤销单位从时间点缩小到 Agent 会话。** 文件的每个修改版本关联对应会话，用户能从版本历史回溯到引发更改的请求，并按会话撤销，而不必倒退整个共享文件夹；若其他人或 Agent 后续改过同一文件，恢复结果存为另一个重命名副本，避免覆盖后来的工作。它提供**可归属、可审阅、可恢复**的产品机制，而不是声称模型不会犯错。

> **核心启示：** `User Intent → Plan Approval → Isolated VM → Host-side Authorization → File Revisions → Conversation-scoped Undo`。模型与文件系统的距离越短，越需要把凭证、许可、版本归属移出模型可控制的执行环境。文章披露产品架构与局部启动测试，但没有给出端到端安全对抗评测或大规模用户成效。

## 2. Agentic AI engineering: Why instructions aren't enough for coding agents

- **作者/来源：** Tobias Zimmergren / 个人工程博客
- **发布日期：** 2026-11-05
- **原文：** https://zimmergren.net/agentic-ai-engineering-03-why-instructions-arent-enough/
- **相关技术：** CLAUDE.md、Claude Code settings.json、PreToolUse / PostToolUse Hooks、PowerShell、单元测试

**推荐理由：** 同样是控制 Agent 的操作权限，个人或团队的 Coding Agent 项目通常没有 Dropbox 那样的虚拟机平台。这篇实战给出仓库内可复现的最小治理结构，包括权限配置、命令解析、构建 Hook、例外审批和 Hook 本身的回归测试；尤其重要的是它揭示了**防护 Hook 自身失效时可能放行命令**的故障模式。

**3 条核心要点：**

1. **文字约束与执行约束必须分工。** `CLAUDE.md` 解释允许做什么、为什么，帮助 Agent 预先规划、减少无效工具调用；`.claude/settings.json` 配置敏感文件的拒读或写入前审批，`PreToolUse` Hook 在命令运行前作出允许、拒绝或请求批准的决定。关键规则在提示与强制层保留双份，但只有后两者可用于执行时拦截；Agent 不得直接修改自己的指令文件，只能提交修改提议。
2. **命令审查应覆盖完整表达式而非首个词。** 作者的 PowerShell Hook 解析整条命令，防止 `git -C . push`、带路径的 `git.exe push`、`cmd /c "git push"`、管道串接等绕过「第一词匹配」的检查；`PostToolUse` Hook 则在编辑后编译受影响项目。约 **250 条命令输入及预期决策**构成 Hook 回归规格，拒绝与审批路径和普通测试一起维护。
3. **安全检查器本身也必须被验证。** 作者发现，在其使用的 Hook 行为下，脚本语法错误、超时或异常退出可能**没有产生预期的拒绝结果**，使原本受限的命令继续执行。因此测试不只检查拦截分类，还检查 Hook 是否正常退出、标准错误是否干净。子 Agent 还需显式收到约束清单。此经验属于作者的具体 Harness 配置，不能把命令字符串解析当成普适沙箱或完整的安全证明。

> **核心启示：** `Readable Rules → Harness Permissions → Pre-execution Hook → Command → Post-edit Build + Hook Tests`。让模型读懂规则是效率优化；让模型**无法越过规则**则需要可执行、可测试的外部控制，并确认失败时如何处理。

## 今日思考

两篇案例的架构规模差距很大，却都把权限从 Agent 的「自我约束」转移到独立检查点：

- **Dropbox：** VM 外的可信宿主掌握访问凭证和文件授权，另外保留会话级修改证据与撤销。
- **Coding Agent：** Harness 权限配置与命令 Hook 拦截操作，测试检查拦截器自己是否仍然有效。

一个可供复用的设计顺序是：

`Describe Constraints → Restrict Capabilities → Authorize Effects → Attribute Changes → Verify Enforcement → Recover`

需要区分三个保证：**Prompt / Skill** 引导计划，**权限与沙箱**限制可执行行为，**审计与撤销**处理已发生的修改。没有一个环节可以简单替代其他环节；两篇文章也都不构成整套防护无漏洞的独立证明。
