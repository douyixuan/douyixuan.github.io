今天选择两篇**原始发布于 2026 年 11 月 9 日与 11 月 3 日**的工程研究与产品实验。Anthropic 把 Coding Agent 推向更大、更长的**软件系统任务**；OpenAI 则把 Agent 接入 CAD、PCB、固件和制造流程，尝试交付**可触摸的实体产品**。两者共同强调：Agent 的能力不应停留在生成代码或漂亮演示，而要接受下游工程约束和独立检验。

## 1. Claude Fable 5.2 and Mythos 5.2

- **作者/来源：** Anthropic / 官方技术发布
- **发布日期：** 2026-11-09
- **原文：** https://www.anthropic.com/claude-fable-and-mythos-5-2
- **相关技术：** Coding Agent、Agent Orchestrator、Subagents、FrontierCode 2.0、FrontierSWE v2、Python→Rust 迁移

**推荐理由：** 值得关注的不是又一个模型排行榜，而是 Anthropic 公布的**长时任务执行样本**：生产服务迁移、千余子代理协作构建系统软件，以及用代码维护者是否愿意合并修改来衡量能力。这些细节提示未来 Software Factory 要同时衡量任务完成度、成本、审查负担和可运行产物；但文中的案例和部分评测来自模型提供方，不能视为独立复现。

**3 条核心要点：**

1. **将评测目标对齐到可合并的软件变更。** 官方报告，在 FrontierCode 2.0 上，Fable 5.2 于 High effort 得到 **45.3%**，约等于 Opus 5.5 最佳设置的 **45.5%**，同时单题成本约为后者一半；Xhigh effort 达 **49.1%**。该基准关注修改是否会被开源仓库维护者接受，比只检查生成代码能否编译更接近真实交付；但成绩受评测设置与成本口径影响。
2. **长时系统任务展示了 Agent 编排能力，也暴露了验证需求。** Anthropic 称一组早期 Fable 5.2 代理将关键生产服务从 Python 迁移为 Rust，启动速度约为原来的 **26 倍**；另一项实验中，模型从空目录出发，在约 **8 天**中协调 **1,000 多个子代理**，产出可在笔记本启动、包含驱动、文件存储、图形窗口和登录功能的操作系统原型。它们是具体工程案例，而非说明所有迁移或系统开发都具备相同成功率。
3. **将模型角色与任务复杂度匹配，而不是让最强模型接管一切。** 发布材料建议一般编码先用 Opus 5.5，将 Fable 用于更困难、开放的任务；也可让 Fable 担任向小模型派活的 Orchestrator，或被其他模型按需咨询的 Advisor。Fable 与 Mythos 使用同一基础模型，但面向不同敏感领域的访问和防护边界不同。复杂任务需要同时记录**模型选择、实际执行轨迹与最终验收证据**。

> **核心启示：** 长时多 Agent 协作把「能否生成代码」变为「能否完成可合并、可运行、可审核的系统变更」。发布方的内部案例和分数提供研究线索，但不足以代替跨项目、跨模型的独立回归评测。

## 2. Accelerating engineering for the physical world

- **作者/来源：** OpenAI / 官方研究与工程团队
- **发布日期：** 2026-11-03
- **原文：** https://openai.com/index/accelerating-engineering-for-the-physical-world/
- **相关技术：** GPT-6 Astra、Codex、CAD、ECAD、PCB、固件、FEA、BenchCAD 2.0、制造审查

**推荐理由：** 这是一条与传统 Coding Agent 不同的交付路径：模型既要生成软件，还要处理电路连接、机械公差、器件封装、制造图纸和外部仿真工具。文章包含**实物原型与失败边界**，比仅展示自动生成 3D 图片更适合思考 AI-native 产品及工程工具链将如何形成反馈闭环。

**3 条核心要点：**

1. **从自然语言需求走向真实硬件，但制造可行性仍是硬边界。** OpenAI 使用 GPT-6 Astra 定义一个与 Codex 对话设备的功能需求、外壳和内部结构、PCB 元件与连线、界面、固件及软件集成。两名团队成员在不足一周内完成设计测试，代工厂在不足一个月内制作小批量原型。不过模型**未能稳定满足制造限度、公差与装配细节**，进入生产前仍需多轮人工审查和修改。
2. **完整反馈链横跨 CAD、ECAD、仿真与组织协作。** 内部团队使用 Codex/ChatGPT 生成和修改 CAD、从 3D 转换制造用 2D 图纸、设置有限元分析（FEA），并检查跨专业设计冲突。自 2026 年 2 月以来，硬件团队模型 Token 使用量增长 **23 倍**；这反映采用规模，**不是生产率提升 23 倍**。外部案例包括从扫描件重建可编辑 CAD，以及为汽车外形提出变化后运行气动仿真。
3. **建立任务指标，但不要把局部基准当作全生命周期验收。** BenchCAD 2.0 检查 3D 零件/装配重建和电路连接识别；文章报告较新的内部模型平均分 **0.875**，GPT-6 Astra 最高推理设置为 **0.594**。该指标没有覆盖采购、制造良率、装配可靠性与实际安全性。因此 OpenAI 让行业工程师审查正确性及可制造性，保持人类对最终成果的验收权。

> **核心启示：** AI-native 工程 Agent 的交付物可以是 CAD、PCB、可运行固件甚至实物；验收不能只靠模型或代码测试，必须连接仿真、制造限制、人工审图与现场结果。

## 今日思考

两篇文章处理的是同一问题的两种极端：

- **软件系统：** 长时运行、子代理协调与跨语言迁移使可观察性和独立审查变得关键。
- **实体产品：** 生成代码只是其中一环，尺寸、公差、电路连接、成本与制造约束都能否决一个表面上完成的方案。

一种有用的交付模型是：

**Intent → Domain Constraints → Agent / Tools → Executable Artifact → Independent Evaluation → Human Acceptance**

值得追问的不是「Agent 最多能干多少小时」，而是：**交付物如何定义完成，验证器与生产环境相隔多远，失败时能否追溯最初的假设？**

两篇均为原始机构发布的案例与评测，统计数字来自各自官方材料；本文区分了可观察的工程成果、内部基准与尚未被普遍验证的能力边界。
